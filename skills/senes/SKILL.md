# senes

senes はユーザー個人のミニマルなtodoサーバー。`senes` CLI は HTTP で `$SENES_URL`（デフォルト `http://127.0.0.1:7878`）のサーバーと通信する。

## ステータスの意味（最重要）

**ステータスの主語は常にユーザー**。Claude 自身の状態ではなく「ユーザーから見てそのタスクがどういう状態か」で選ぶ。

| status | 意味 | 典型例 |
| --- | --- | --- |
| `doing` | **ユーザーが手を動かす番**のタスク | Claude の作業が終わりユーザーのレビュー・確認待ち／Claude がユーザーの判断・入力を必要として止まっている／ユーザー自身が作業中 |
| `waiting` | **ユーザーが他人・AI agent 等の作業を待っている**タスク | Claude（や他の agent）が作業中／PR のレビュー待ち／CI・デプロイ待ち／他チームの返答待ち |
| `todo` | まだ誰も着手していないタスク | 登録しただけ |
| `backlog` | 当面着手する予定のない後回しタスク | いつかやる／優先度が低く今は手を付けない |
| `done` | 完了 | ユーザーが完了と認めたもの |

### よくある間違い

- **Claude が作業を始めるときに `doing` にしてはいけない。** Claude が作業している間、ユーザーは Claude を待っているので `waiting` が正しい。
- Claude が作業を終えたら `done` ではなく、原則 `doing` に戻す（ユーザーが成果物を確認する番になるため）。`done` にするのはユーザーが明示的に完了を指示したときか、ユーザーのアクションが一切不要であることが明らかなときだけ。
- Claude が途中で質問・確認のために止まるときも `doing`（ボールがユーザーにある）。
- PR を作成してレビュアーのレビュー待ちになったら `waiting`。ただしユーザー自身がまず PR をセルフレビューする必要があるなら `doing`。

迷ったら「今このタスクのボールを持っているのはユーザーか（→ `doing`）、ユーザー以外か（→ `waiting`）」で判断する。

## コマンド

```sh
senes ls                     # done以外をstatus別に一覧（-a で done も含む）
senes ls todo doing          # statusで絞り込み
senes show <id>              # タイトル・status・説明を表示（id は "#12" 形式も可）
senes add "<title>" [-d "<desc>"] [-s <status>]   # 作成（デフォルト status: todo）
senes edit <id> [-t "<title>"] [-d "<desc>"] [-s <status>]
senes mv <id> <status>       # status だけ変更
senes mv <id> [<status>] [-top|-bottom|-before <id>|-after <id>]   # 並び替え（列内の順序 = 優先度）
senes rm <id>...             # 削除
```

- 説明欄（description）は GitHub Flavored Markdown。`- [ ]` のチェックリストや PR URL を書ける（Web画面では PR の状態がアイコン表示される）。
- GitHub の PR に言及するときは `#34` や `owner/repo#34` ではなく、必ずフル URL（`https://github.com/owner/repo/pull/34`）で書く。URL で書かないと Web 画面で PR の状態が表示されない。
- `-d -` で説明を stdin から読める。複数行はヒアドキュメントで渡す。

```sh
senes edit 12 -d - <<'EOF'
...
EOF
```

## 説明欄を更新するときの注意

`senes edit -d` は説明欄を**丸ごと置き換える**。追記したいときは必ず先に `senes show <id>` で現在の内容を取得し、既存の内容を保持したうえで追記した全文を渡すこと。ユーザーが書いた内容を消さない。

## タスクを取って作業するときの流れ

1. **タスクを選ぶ**: ユーザーが ID を指定していればそれを使う。指定がなければ `senes ls` で一覧を見て、候補をユーザーに提示して確認する（勝手に選ばない。ただしユーザーが「次のを取って」などと任せている場合は `todo` から妥当なものを選び、選んだ理由を一言添える）。
2. **内容を把握する**: `senes show <id>` で説明欄を読み、リンクされた PR・Issue・ドキュメントなどを確認する。
3. **着手を記録する**: `senes mv <id> waiting`（Claude が作業する＝ユーザーは待つ側）。
4. **作業する**: 必要に応じて、進捗・判明したこと・作成した PR の URL などを説明欄に追記する（上記の注意どおり既存内容は保持）。チェックリストがあれば完了した項目を `- [x]` にする。
5. **ユーザーに返す**:
   - 作業が終わってユーザーの確認が必要 → `doing`
   - ユーザーの判断・情報が必要で止まった → `doing`
   - PR を出してレビュアー待ち、CI 待ちなど他者待ち → `waiting`
   - ユーザーが完了を明言した → `done`
   最後に、どのステータスにしたかと理由をユーザーに一言伝える。

### `doing` / `waiting` に移すときは説明欄の冒頭に状況を1文で書く

ステータスを `doing` または `waiting` に移すときは、説明欄の**冒頭**に以下を簡潔に書く。詳細はセッション内で伝えるので、説明欄には書かない。

- **`doing` に移すとき**: ユーザーに何を依頼したか（ユーザーにしてほしいアクション）を1文で書く。
  - 例: `> 依頼: https://github.com/owner/repo/pull/34 をセルフレビューしてマージしてください`
- **`waiting` に移すとき**: 何を待っているか、次に何が起きたらステータスが変わるか（変わった後のステータスも）を書く。
  - 例: `> 待ち: Claude が実装中。実装が終わりユーザーの確認が必要になったら doing`
  - 例: `> 待ち: https://github.com/owner/repo/pull/34 の @reviewer のレビュー待ち。approve されたら doing（マージ作業）`

ルール:

- 既存の説明欄は保持し、その前に足す。前回の `> 依頼:` / `> 待ち:` 行が冒頭に残っていれば置き換える（両方を並べない）。
- 上記「タスクを取って作業するときの流れ」の手順3（着手時に `waiting` にする）でも `> 待ち:` を書く。

## タスクを新規登録するとき

- 作業中に派生タスク（後回しにする修正、フォローアップなど）が見つかったら、ユーザーに確認してから `senes add` で登録する。
- タイトルは一覧で見て分かる短い文にし、詳細・背景・関連 URL は `-d` に書く。
- status は上記ルールで選ぶ（誰も着手しないなら `todo`、他者に依頼済みで返答待ちなら `waiting` など）。

## その他

- `senes rm` はユーザーが明示的に削除を頼んだときだけ使う。完了したタスクは削除せず `done` にする。
- `cannot reach senes server` エラーが出たらサーバーが起動していない。ユーザーに `senes serve` の起動を依頼する（`SENES_URL` が別ホストを指している可能性もある）。
- 1つの作業で複数タスクを触る場合も、ステータスはタスクごとに「ボールが誰にあるか」で個別に判断する。
